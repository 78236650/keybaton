# 设计文档

为什么是现在这个样子：威胁模型、关键取舍、以及被否掉的方案。

---

## 1. 问题

AI agent 要干活，就需要账号密码。现在业界的做法按糟糕程度排序：

1. 把密钥写进 prompt / 环境变量 / `.env`，agent 直接看见明文
2. 人在聊天里发密码，agent 抄进代码
3. 用 Vault 一类系统，但为了接 agent 又写一层适配，适配层自己成了新的泄漏面

三种做法有同一个漏洞：**凭据一旦进入 agent 的上下文，就再也收不回来**。提示注入、日志、上下文缓存、模型厂商的留存策略，任何一条都能把它带走。

## 2. 威胁模型

**假设被攻破的**：agent 本身、它的上下文、它运行的进程。

**要守住的**：凭据不得进入 agent 的上下文；即使进入，也要能被发现和追溯。

**明确不防的**（诚实写在 README 里）：
- 本机进程能读 `~/.keybaton/master.key` —— 单机方案的固有限制
- 拿到 `KEYBATON_TOKEN` 的人可以调 `kb_http` 用你的凭据发请求（但拿不到明文）
- 目标服务自己把凭据回显出来的情况（做了脱敏，但不可能覆盖所有编码变形）

## 3. 核心设计：两种交付模式

| 模式 | 适用 | 凭据去哪 |
|---|---|---|
| **注入环境变量**（`keybaton run`） | 本机进程、CI、脚本 | 子进程环境变量 |
| **服务端代发**（`kb_http`） | 远程 agent、不可信进程 | 不出服务端，直接进 HTTP 请求头 |

第一种是"人机一致"的便利模式，第二种才是安全模式。**默认没有 `kb_get`**，就是这个取舍的直接体现。

### 为什么不做"发一个短期 token 给 agent"

短期 token 看起来更简单，但凭据仍然在上下文里——只是有效期短。对提示注入毫无防御力。否掉。

### 为什么不做 egress 代理（HTTP 代理层）

代理能覆盖任意协议，但要做 HTTPS MITM 与证书信任，部署复杂度陡增，而 80% 的场景是调 REST API。当前版本用"服务端代发"覆盖 REST，把代理留给后续版本。

## 4. 数据模型

```sql
secrets(id, name UNIQUE, username, note, cipher, nonce, created_at, updated_at)
audit(id, ts, actor, action, target, ok, detail)
```

- 每条密文独立 nonce（12 字节），AES-256-GCM
- 主密钥 32 字节，存 `master.key`（0600）或 `KEYBATON_MASTER_KEY`（base64）
- 明文只在 `Get` 的返回瞬间存在于内存

**没有**做：字段级加密（username/note 是明文）、密钥轮换自动化（v0.2）、多租户（不在定位内）。

## 5. 鉴权与授权

单令牌模型：`--token` 或 `KEYBATON_TOKEN`，一个服务一个令牌。

**为什么不按 agent 发多令牌**：v0.1 的目标是"一个进程/一台机器"的最小可用；多令牌 + 按条目授权属于团队版。当前用"每台机器一个实例"来隔离，比一个实例里做多租户更简单也更安全。

## 6. 关键取舍

| 决定 | 取 | 舍 | 原因 |
|---|---|---|---|
| 语言 | Go 单二进制 | Python/Node（生态更好） | 分发体验决定开源工具的第一印象；交叉编译零依赖 |
| 存储 | SQLite | PostgreSQL | 单机场景不需要服务端数据库 |
| 加密库 | 标准库 crypto/aes | 第三方 KMS | 少一个依赖，少一个供应链风险 |
| SQLite 驱动 | modernc.org/sqlite（纯 Go） | mattn/go-sqlite3（CGO） | 交叉编译不需要三套 C 工具链 |
| 接口 | MCP over HTTP JSON-RPC（自己实现） | 官方 SDK | 三个方法约 100 行，避免 SDK 版本漂移 |
| 明文入口 | 默认关闭的 `kb_get` | 默认开放（更"好用"） | 好用和安全的边界就在这一行 |

## 7. 脱敏

`kb_http` 拿到上游响应后，会把响应体里出现的敏感串替换成 `[REDACTED-BY-KEYBATON]`，包括：

- 明文本身
- `base64(username:secret)`（basic 模式的形态）

**做不到的**：URL 编码、HTML 实体、分段拼接、压缩后的形态。这是"尽力而为"，不是密码学保证——README 与 SECURITY.md 都写明了。

## 8. 出站请求的两道闸

1. **禁止跨主机重定向**：302 到别的域名直接报错，防止凭据被带去第三方
2. **响应体截断 64KB**：避免把大文件灌进上下文（也顺带防了内存放大）

## 9. 未采用但考虑过的方案

| 方案 | 结论 |
|---|---|
| 直接内嵌 Vault Agent | 运维成本高，与"单容器"定位冲突 |
| 用 age 做文件加密 + `sops exec` | 只能做 env 注入，没有审计与代发能力 |
| 做浏览器插件 | 那是给"人"用的密码管理器，不是我们的场景 |
| 做 K8s Operator | 客户群不匹配，v0.x 不做 |

## 10. 后续

- v0.2：TOTP 代取（种子不出服务端）、`--file` 注入、导入 1Password/Bitwarden
- v0.3：团队模式（多令牌 + 按条目授权 + 审批流）
- 不做：图形界面、浏览器插件、SaaS
